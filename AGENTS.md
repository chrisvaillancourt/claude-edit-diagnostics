# edit-diagnostics

A Claude Code mod (function-hook plugin). `README.md` is the user-facing spec; keep it in step with any behavior change in the same commit.

## Layout

- `hooks/parse.ts`: the output parsers, one small parser per format (`tsc`, `ruff-json`, `json`). Pure, bounded, strict: anything a parser doesn't recognize is a parse failure, never a skipped line. Pinned by the standing corpus in `parse.test.ts`, built from real output captured on Claude Code's host (TypeScript 5.9.3, ruff 0.17.2). Every parser bug reported becomes a row there.
- `hooks/policy.ts`: pure decisions and text. Options, command parsing, the config schema and its validation, globs, path folding, the run plan (which checks, which operands), finding fingerprints and the novelty ledger, and the text the model reads. No `$`, no I/O. Unit-tested in `policy.test.ts`.
- `hooks/register.ts`: wiring. `tool.call` (record successful mutations; tool-mode delivery), `classic.PostToolBatch` (batch-mode delivery), `turn.start` (batch-mode health), the command, `$.process.spawn` (bounded by a `$.clock.after` timer), `$.fs`, `$.store` approvals and `$.state`. Keep logic thin here; test behavior through the engine in `register.test.ts`.
- `types/index.d.ts`: the mod's types and its `$.state` contract (`PluginState['edit-diagnostics']`). Every `$.state` key the module uses must be declared here.
- `.claude-plugin/plugin.json`: manifest and `userConfig` options. `marketplace.json` makes the repo its own marketplace.
- `scripts/check.sh`: the commit gate (validate, test, typecheck).
- `.claude-plugin/types/` and `tsconfig.json` are generated by Claude Code when it loads the mod from a watched folder. They're gitignored; don't commit or hand-edit them.

## How it works (design invariants for this mod)

- **Feedback only.** The native tool result is passed on unchanged (`ref`, `text`, `result`, any `context` from below); the mod only appends one `context` entry (tool mode, or the batch-mode "pending" note) or returns `additionalContext` (batch mode). Findings never deny, undo or rewrite an edit. A denied or errored call (`deny`, `isError`) triggers nothing.
- **Main loop only.** `tool.call` with `e.agentId` set and `classic.PostToolBatch` with `agent_id` set return `next(e)` untouched.
- **What counts as a mutation.** A successful native `Edit` or `Write` (`e.file_path`) or `NotebookEdit` (`e.notebook_path`). The path is resolved with `$.fs.stat(path, { resolve: true })`; it must be a regular file whose `realPath` lies under the root's `realPath`. Anything else (Bash, MCP tools, files outside the root, links that escape it) is out of contract and ignored. MultiEdit is not a tool in 2.1.310.
- **The root** is the session's `cwd` at `session.start`, resolved. The config is `<root>/.claude/edit-diagnostics.json`, read fresh before every run: no ancestor search, no auto-detection of checkers.
- **Approval is by exact text.** `$.store` key `approval:<root>` holds the config text the person approved. A run happens only when the file's current text equals it, so any change (the model editing the config included) makes the mod inactive until the person approves again. `/edit-diagnostics approve` is accepted only from `origin.kind === 'composer'` (the person's Enter); a plugin, the SDK (`claude -p`), a peer or any other origin is refused. Approve refuses an invalid config. Headless sessions use an earlier approval or stay inactive. Inactive-because-unapproved (or invalid, or changed) is said once per distinct config text: in a `context` note to the model and in `$.ui.log`.
- **Delivery has two modes** (`delivery` option):
  - `tool` (default): after each successful mutation, `tool.call` runs the checks over every pending path and appends the report as `context`. Default because on 2.1.310 a built-in managed plugin passed `classic.PostToolBatch` on past user-tier plugins live, so batch delivery never ran.
  - `batch`: registered only in this mode (the hooks below are not registered at all in tool mode). `tool.call` records the path and appends "checks pending; not verified yet"; `classic.PostToolBatch` runs once over all pending paths and returns `additionalContext`. If the batch hook never runs, the model keeps seeing "pending", never a clean result, and the next main `turn.start` that finds paths still pending logs once that the batch hook was skipped and `tool` delivery is needed.
- **One run at a time, by ownership.** A run claims `running: { runId, loadId, paths }` with a versioned `update`, taking every pending path. A mutation that finds a live claim leaves its path pending and says "not verified yet; an earlier check run is still going". A claim whose `loadId` isn't this module load's (a reload or a lost worker) is stale: its paths go back to pending. Right before each subprocess starts, the run re-checks with a versioned `update` that `running.runId` is still its own and the mod is on, and stops starting checks once it isn't. After the processes finish, the run applies its results only under the same check; `/edit-diagnostics off`, `revoke` and a `/clear` (whose new session reads empty state) make it drop them. A child already running when `off` arrives still runs to its exit or timeout.
- **Bounded execution.** Checks run sequentially through `$.process.spawn({ argv, cwd })`: no shell. Not `$.process.run`, which reads a child ended by a signal as exit code 1, which every parser accepts, so a killed checker's partial output passed as complete. A `$.clock.after(timeout)` timer closes the stream, which kills the child; the hook only awaits the stream's pulls (engine calls), never a local promise. Per-check timeout `timeoutMs` (default 5 s, 0.5–30 s), aggregate `batchTimeoutMs` (default 10 s, 1–30 s); a check gets the smaller of its timeout and what's left. A check that can't start for lack of budget is "not run: time budget used up". Combined stdout+stderr past 512 KiB closes the stream and is "not verified: output too large". A child ended by a signal is "not verified: ended by SIG…". At most 50 file operands per check per run; the rest are reported "not checked".
- **Not verified means not verified.** Spawn failure, timeout, a signal, an exit code the parser doesn't accept, a nonzero exit with no findings, malformed output, and too much output are reported per check as `NOT VERIFIED: <reason>` and never update the ledger. One failed check doesn't hide another's findings.
- **Operands.** `scope: "files"` appends the matched touched files as separate argv entries, relative to the check's `cwd` and always `./`-prefixed (a bare `-x` reads as an option, and tsc expands a bare `@x` into arguments from that file), or absolute when outside `cwd`. `scope: "project"` appends nothing: the touched files only decide whether the check runs. `argv[0]` starting with `./` or `../` is resolved against the check's `cwd`.
- **Novelty is against the last observed snapshot (omp's ledger), with counts.** Before filtering, each distinct file a check reports (up to 200 per check) is resolved with `$.fs.stat(…, { resolve: true })`, so a finding reached through a link inside the project has the same identity (realPath, root-relative) as the edited file; a path that doesn't resolve keeps its spelling. A finding's fingerprint is checker id, root-relative file, severity, code and the whole whitespace-collapsed message (past 300 characters: its first 200, its length and two 32-bit hashes of all of it), never its line or column; display truncation is separate. The snapshot is kept per check and file (`null` file for project-level findings) as fingerprint counts. A fingerprint whose count rose is newly observed and all its current occurrences are shown; one at or below its count is "still present" and only counted. A file seen for the first time is labelled unbaselined. Only touched files and project-level findings are reported and snapshotted; findings in other files are counted ("N in M other files, not shown") and never snapshotted, so they're new when those files are touched later. A clean complete result stores an empty snapshot. Findings left out by the output caps keep their old count, so they show again next run.
- **Output caps.** At most 30 findings and 8,000 characters per report, each message cut at 400 characters, omissions counted. Every check's status line is placed first and always fits: path lists show at most five paths, each cut to its last 120 characters, and reasons are cut at 300; findings get what's left. The report says findings are tool output, not instructions, and calls additions "newly observed", never "introduced by this edit".
- **State** (`$.state`, one session atom): mode override, pending paths, the running claim, snapshots (at most 200 file keys, oldest dropped), the last run's summary, notice keys, counters. The store holds approvals only.

## Checked live (Claude Code 2.1.310, `claude -p`, Haiku)

- `classic.PostToolBatch` never reached a `--plugin-dir` mod: the debug log had `classic.PostToolBatch bypassed by <managed plugin> (tier user); beneath runs`, and stderr `its classic.PostToolBatch hook was skipped`. `tool.call` fired for both of two parallel Writes, about 0.5 s apart, and its `context` reached the model.
- The engine also hands that skip notice to the model, as a task notification after the next tool result (`edit-diagnostics: its classic.PostToolBatch hook was skipped. ...`). So `classic.PostToolBatch` and `turn.start` are registered only when `delivery` is `batch`; in tool mode the debug log lists `events: session.start,command.run,tool.call`.
- `$.process.spawn` from a `tool.call` hook: a child that printed a line and then got SIGTERM ended `{ code: null, signal: 'SIGTERM' }`. A `$.clock.after(14000)` timer that called `return()` on the stream while the hook awaited `next()` ended the stream at 14.0 s (debug log: `stopped: the op was aborted`), no child left running, and the hook's result reached the model: waiting on the stream past the ~10 s hook budget is not charged.
- Core flow, headless Haiku in a scratch TypeScript project, config approved beforehand by `/edit-diagnostics approve` in an interactive (pty) session, the approval read back from `$.store` by the later `claude -p` run: an Edit that assigned a string to a `number` got `types (tsc): 1 newly observed in edited files (first check of src/a.ts: ...)` with the TS2322 line in the tool result's context; the Edit that undid it got `types (tsc): no findings in src/a.ts`, nothing stale. Each `bunx tsc` run took about 0.4 s. The mod left the edited bytes as the Edit wrote them.

## Commands

```sh
scripts/check.sh            # claude plugin validate . && claude plugin test . && typecheck
scripts/check.sh --no-tsc   # when TypeScript isn't available
```

All gates must pass before every commit. A behavior change needs a test in `hooks/*.test.ts` (the `claude-code/testing` kit: `mock.clock`, `mock.store`, `mock.env`, and `on(...)` hooks that stand for the engine beneath the plugin) written first and seen failing for the intended reason, then the change that makes it pass.

To try the mod in a live session: `claude --plugin-dir .` (interactive sessions hot-reload on save), or `claude -p --plugin-dir . "<prompt>"` for a headless run (always loads fresh; hooks that need a terminal won't fire). `claude --debug` logs every skipped hook and refused result.

## Design invariants (apply to every mod built from this template)

- **Main conversation vs subagents.** Events from a subagent's loop carry `e.agentId` (`agent_id` on `classic.*` events). Decide explicitly whether the mod acts on subagents; by default return `next(e)` early for them.
- **Hot reloads reset module variables** (timers included). `register` and `session.start` run again; `$.state` and `$.store` survive. Anything that must persist goes in state or store. Change an atom's `shape` tag when its stored type changes.
- **Never throw out of a hook or timer for reporting.** Logging, status and toasts are best effort. A hook that guards (denies a tool call, drops a prompt) gets a `.catch` that decides fail-open or fail-closed deliberately (`next.called ? next(e) : { deny }`).
- **Headless sessions** (`e.isInteractive === false`, `claude -p`) have no terminal: no panes, `$.ui.notify` fails, `$.session.compact` rejects. Skip or degrade explicitly.
- **Cost and the prompt cache.** Anything that calls a model (`$.model.complete`, `classify`, `fork`, `$.agent.spawn`) is billed to the person. Say what it costs in the README, bound it with options, and don't change the system prompt or tool list per turn (that rewrites the whole prompt cache).

### Engine constraints found the hard way (Claude Code 2.1.29x–2.1.310)

- `$.prompt.submit` is refused from inside a `command.run` hook (it would wait on the turn the hook holds). Submit from a `$.clock.after(0, …)` timer.
- `$.session.compact` rejects while a turn runs and in headless sessions.
- A plugin's submitted prompt never expands `@` mentions; `$.prompt.fill` lets the person send it instead.
- `$.model.fork` replays the main thread's last request, which ends before the turn's final answer: quote the answer into the fork prompt if the fork needs it.
- The engine already prefixes `$.ui.status`, `$.ui.toast` and command output with the plugin name; don't add `edit-diagnostics:` there. `$.ui.log` lines keep the prefix.
- A model `Write` outside the project raises a permission prompt; have the plugin write its own files with `$.fs.write` (it creates directories). `$.fs.write` replaces the whole file; there is no append.
- `turn.step` hooks are async generators in the path of every request: always pass the stream through (`yield* next({ ...e, effort })`). A rewritten `model` must be a full id (`claude-haiku-5-5`); an alias failed with `unrecognized_model`. Changing `effort` per request keeps the prompt cache (Opus, Sonnet, Haiku 5.5); changing `model` rereads everything uncached. The UI keeps showing the session's model and effort, so surface a rewrite with `$.ui.status`.
- `tool.call`: `const r = await next(e); return { ...r, context: [text] }` adds text the model reads after the tool result and the person never sees; `{ deny: reason }` blocks the call. A `tool.call` hook without `.catch` is reported by validate as a gate: give it one that fails open or closed on purpose.
- Haiku 5.5 rejects `temperature`/`top_p`/`top_k`, `budget_tokens` and assistant prefill with a 400. Prices step up 5x above 100K prompt tokens.
- Side calls (forks, completions, subagents, compaction) use the "everything else" prompt-cache bucket (5m on a subscription), not the main conversation's 1h one. Cache reads still count against plan usage.
- Text a hook injects for the model must not talk about the model's thinking or reasoning ("you can't see it", "doesn't count"): Opus 5.5's reasoning-extraction safeguard refused such a request. Phrase it in terms of the reply and the work.
- Don't build on instructions the model can ignore: a gate that "asks" the model to do something first failed live. Enforce in a hook, or give the model the information and let it decide.
- `/clear` is `session.end` with `reason: 'clear'` and no `session.start` after it: reset per-conversation state there. After a `/clear`, `$.state` reads empty (version 0) for the new session, while module variables survive: anything that must cross a `/clear` (a "not sent" list, an epoch) has to be carried in a module variable from `session.end` and adopted into the new session's state. A `$.clock.after(0, …)` timer started in `session.end` fires in the new session (about 20 ms later; `$.session.id()` already returns the new id, and a `$.state.set` there is what later hooks read), but `session.end`'s own awaited work can outlast it: keep retrying until the id has switched, and adopt on any earlier access too. Adoption moves everything the carry holds. Only a reload before adoption loses it.
- **Hook-owned time has a budget (about 10 s).** Time spent in a `$` call or `next` doesn't count; time awaiting the mod's own promises (a local queue, a semaphore, a timer) does, and the engine refuses the dispatch when it runs out. Never make a hook wait on local state: keep one of the hook's own `$` calls in flight, or move the work to a timer. A second request that arrives while one is running is better refused at once than queued behind it.
- **The hooks worker has a 5 s heartbeat.** Synchronous work that doesn't yield for about 5 s (masking a 4 MB output with a per-value `indexOf` loop, an exponential schema walk) gets the worker replaced; the registration's `.catch` then runs in the new worker, and whatever the old one hadn't done yet (a cleanup write) never happens. Put persisted state in its safe form before any unbounded work (write the marker first, then do the work, then write the result), keep per-item scans single-pass, and bound validators and parsers with a work budget whose exhaustion is a failure, never a pass.
- **`$.state.get` can return a stale snapshot** within a dispatch (seen live: a plain read returned this module's earlier write after another hook's later one). To check ownership right before a side effect, use a versioned `update` that writes the same value back; it retries on a version miss. It's a freshness check, not a lock: re-check after every `await` and immediately before each `$.prompt.submit`, `$.turn.abort` or `$.session.append`.
- **Design async ownership as one state machine** (a pure `transition(state, event) → { state, actions }`, every event applied in one `update`) once a mod has corrections, holds or releases that can race newer input, `/clear`, off switches or reloads. Patching individual checks kept failing review; the state machine passed.
- `turn.start` and `turn.complete` fire for subagents too (`e.agentId` set) on 2.1.310. Track the main turn by id and consume its completion once.
- A plugin seated above yours (a managed plugin, prepend tier) can pass an event on past your hook: `prompt.context`, `prompt.attachment`, classic hooks and some `session.append` rows were skipped this way live. Don't build a guarantee on a hook firing; document it. On 2.1.310 `classic.SubagentStop` was skipped this way too. In that setup plain subagents report back through a `SubagentHandback` tool call (the Agent result is only a pointer), and denying that call re-prompts the child, so it can serve as a stop gate; detect per child which path is in use rather than hard-coding one.
- `session.append` can't rewrite attachments rendered per request (`@file` content); `prompt.attachment` is the hook that can. The raw attachment payload still persists in the transcript.
- On 2.1.310 a `prompt.submit` answered `{ drop }` leaves the typed text in the prompt box. Clearing it by reading the box and replacing it races the person's typing: never replace the whole box from an earlier read.
- `$.prompt.fill` is refused while a focused pane holds the keys: close the pane first. Button hotkeys fire even while a text field is drawn, and a Button and an Input sharing a `key` sends focus to the Button.
- `$.process.spawn` ends the child it started when the stream is closed (`return()`), and an ordinary process tree dies with it while that child is alive (seen live, 2.1.310). It offers no process-group or detach control: a wrapper that dies while its own child holds stdout/stderr leaves that child reparented to PID 1, and closing the stream doesn't reach it (a review's orphan probe on 2.1.310 saw it keep running past the timeout). Document it; don't signal Claude's own process group.
- `$.fs.read` refuses files over 4 MiB (transcripts pass 50 MB); `$.process.spawn` of `tail -c +N` reads incrementally.
- **The re-entry rule.** A `$.prompt.submit` the mod makes while one of its hook dispatches is still running (inside `turn.complete`, inside a `ui.press` hook, from a timer that fires before that dispatch settles) passes through the mod's own `prompt.submit` hook. One made from a `Button`'s `onPress` closure, or from a timer that fires after the mod's hooks returned (the `$.clock.after(0)` a `command.run` hook starts), skips it (`prompt.submit skipped: re-entry`). A check that must see the mod's own submits has to submit from a hook path. `$.prompt.submit` carries no id: correlate admissions FIFO and by epoch, never by text (another plugin may rewrite it).
- **Plugin options through `/config`.** `$.config.list()` lists a plugin's option rows only in interactive sessions (headless lists none, `--plugin-dir` and installed alike), and a row's `key` is `<plugin name>.<field>` while its `provider.plugin` is the plugin id (`name@marketplace`, `name@inline`): find rows by key. `$.config.set` answers `{ value }` with what was actually written (another plugin's hook may clamp it): install and report that, not the proposal. There is no compare-and-set; read the row right before writing. Headless, print the value to save and `claude plugin configure <id> --values-stdin`.
- A plugin tool's result must be a string (`JSON.stringify` structured answers); the test kit accepted an object that the engine refused ("does not match its output shape").
- The native Agent tool takes an `effort` input that a `tool.call` hook can set before `next` (`agent.spawn` can set `model` but not effort). In auto mode, rewriting a tool call's input makes the safety classifier (an engine-owned model call) judge that call: say so in the README's cost section.
- `$.process.run` is logged in the debug log by executable, argument count, exit code, time and output size, never its output; reading the environment with `['/usr/bin/env', '-0']` needs no permission prompt. The hooks sandbox has no `eval` or `new Function`: ship plugin-local interpreters (a schema validator, a parser) as plain code.
- The hooks sandbox treats `__proto__` as an ordinary own key: use `Object.hasOwn` (or a `Map`) for every lookup keyed by user text (rule names, schema properties).
- `$.model.classify` takes only labels: no rubric, timeout, effort or usage. `$.model.complete` with a rubric and `timeoutMs` worked better for judges. Haiku replies have exceeded `maxTokens`; don't promise an output bound.
- Parallel cold requests each write the prompt cache; send one request first when many share a long cached block.

### Bugs that recur in these mods (check every change against them)

Reviews of relay, defer-queue and prewalk kept finding the same family: a boolean flag left stale by a late event (track the running `turnId` instead), a message lost on a path nobody tested (a refused submit, a release racing a new hold), a timer or async step acting for a run that was cancelled or replaced (guard with a `runId` and re-check after every `await`), state that survived `/clear` or a reload when it shouldn't (or didn't when it should), and engine state copied into the mod's own flags (decide from facts at decision time). Two review rounds of blockers in the same mechanism means change the mechanism.

When review findings keep moving the same edge, ask whether the design is causing it before patching again. Two cases from these mods:

- **Heuristic detectors and parsers:** one regex serving five syntaxes had no correct boundary, so each fix broke a neighbouring format. What held instead: write the contract first (the sources and formats covered, each with its own small parser, plus an explicit out-of-contract list in the README), and keep a standing table-driven corpus (exact expected values; everything else byte-identical; every past review repro as a row) that runs on every change. Reviews then judge against the contract, and an out-of-contract miss is a feature request, not a bug.
- **Async ownership across `/clear`:** see the state-machine and carry rules above. Prefer removing moving parts (one record owns the queue; adoption moves all of it) to adding guards.

### Test kit notes

- A hook that answers an op on `$` (`command.register`, `fs.read`, `model.complete`, `ui.toast`, `session.messages`) returns `{ value }` or `{ deny }`; a hook that answers an event (`session.start`, `turn.start`, `turn.complete`) returns the event's result directly.
- One bottom hook per event per test file (a second registration errors). Test files with JSX are `.test.tsx`.
- Use `mock.clock(on)` and `clock.advance`/`settle` for time; there is no `setTimeout`.
- A throwing mock hook is skipped rather than surfacing its error, so test decisions that depend on an error's text as pure functions in `policy.ts`.
- Any helper that receives `$` must be a top-level function: the engine's static check refuses a module that passes `$` to a closure defined inside `register`. `atom({ plugin, key })` takes string literals, not a const.
- The kit accepted a wrong tool-input shape at runtime that `tsc` caught: run the typecheck.
- A test's `process.spawn` stand-in is an async generator that yields chunks and returns `{ value: { code, signal } }`, or `{ deny }` for a child that can't start; one that returns the bare result or throws is skipped and the call reads `no implementation for process.spawn`.

### Live checks

The test kit stands in for the engine; it can't show what the engine really does. Before building on an engine behavior the types don't state, probe it: a throwaway observer mod (`--plugin-dir`) that logs events with `$.fs.write`, and one short live session, with `--model haiku` to keep it cheap. Record the Claude Code version a behavior was checked on. Headless runs (`claude -p`) create transcript folders under `~/.claude/projects/`; run them from a scratch directory, or set a scratch `CLAUDE_CONFIG_DIR` so the transcripts land there instead (an isolated config dir also lets a probe install the mod with `claude plugin marketplace add` without touching the real setup). A pty driver must wait about 3 s after the workspace-trust dialog draws before sending Down and Enter: keys sent the moment it appears are swallowed, and its default answer exits. Never print the whole environment in a shell (no bare `env`, `printenv` or `set`; in zsh `cmd 2>&1 >/dev/null | head` still sends stdout to the pipe): the session's own tokens are in it.

## Conventions

- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`).
- Bump `version` in `plugin.json` for every release users should get. Installs from GitHub run a copy, and `claude plugin update` only replaces it when the version changes. An install whose marketplace is a local clone runs from the clone itself: edit, then `/reload-plugins`.
- MIT licensed: `LICENSE` at the root, and `plugin.json` says `MIT`. Treat the repo as public: no secrets, tokens, session IDs, personal paths or employer-specific details in code, tests, docs or commit messages.
- Don't add Claude or AI attribution trailers to commits.
